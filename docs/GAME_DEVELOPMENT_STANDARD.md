# 狗耳GAME 网页游戏制作经验与开发规范

版本：1.0
适用范围：狗耳GAME 中新增或重制的休闲、动作、益智、经营、音乐及轻度 Roguelike 网页游戏。

## 1. 文档目标

本规范用于指导新游戏从立项、原型、开发、美术、数值、性能优化到最终验收的全过程。

规范中的关键词含义：

- **必须**：不满足则不能进入下一阶段。
- **应该**：默认执行，只有明确理由才能偏离。
- **可以**：按游戏类型选择。
- **禁止**：已被实践证明会降低质量或引入严重风险。

最终质量标准不是“功能已经存在”，而是：

> 玩家能迅速理解目标，操作立即得到反馈，能够预测行为结果，失败后知道如何改进，并愿意再玩一局。

---

## 2. 产品设计总原则

### 2.1 核心循环必须先于内容开发

每个游戏必须先用一句话描述核心循环：

```text
玩家做什么 → 世界发生什么 → 玩家获得什么 → 玩家下一步为什么继续
```

示例：

```text
瞄准发射彩球 → 彩球插入轨道并形成同色组合 → 消除、得分并减缓失败压力 → 继续寻找连锁机会
```

如果不能用一句话说明核心循环，不得开始批量制作关卡、剧情或素材。

### 2.2 前三分钟体验标准

新玩家进入游戏后：

- 5 秒内必须看懂主要目标。
- 10 秒内必须能够完成第一次有效操作。
- 30 秒内必须获得第一次明确正反馈。
- 3 分钟内必须经历一次节奏变化、成长选择或阶段目标。

禁止用长文本、连续弹窗或复杂系统说明阻塞第一次操作。

### 2.3 乐趣必须至少覆盖两层

游戏至少具备以下两层乐趣：

1. **即时操作层**：移动、射击、摆放、匹配、决策等手感。
2. **短期策略层**：路线、资源、技能、顺序、时机等选择。
3. **长期成长层**：关卡、构筑、排名、角色、解锁等目标。

只有点击等待、数值自动上涨而缺少选择的系统，不得作为核心玩法。

### 2.4 所有行为必须形成完整因果链

玩家行为不能只改变一个数字。重要行为必须表现完整过程：

```text
输入 → 动作开始 → 中间过程 → 命中/到达 → 状态改变 → 视觉与声音反馈
```

例如输油管不能拖完后瞬间完成，应包含预览、计价、钻头下探、接触资源、开始输送等过程。

## 3. 立项规范

每款新游戏必须先填写以下简报。

### 3.1 新游戏简报模板

```text
游戏名称：
游戏类型：
一句话核心循环：
目标玩家：
单局时长：
主要输入方式：
成功条件：
失败条件：
前三分钟体验：
核心资源：
成长方式：
关卡结构：
美术风格：
声音方向：
最高负载场景：
参考玩法：
与参考作品的差异：
```

### 3.2 立项通过条件

- 核心循环能在一周内做出可玩原型。
- 成功与失败条件明确。
- 玩家每 10 至 30 秒至少需要做一次有意义的判断。
- 玩法不是对大厅已有游戏的简单换皮。
- 素材来源、制作方式和授权风险可控。
- 已定义最低可玩版本，不以“以后加内容”掩盖核心玩法不足。

## 4. 制作阶段与质量门禁

### 阶段 A：规则原型

目标：验证核心玩法是否成立。

必须完成：

- 基础输入。
- 核心规则。
- 成功与失败。
- 最简单的临时画面。
- 一局可从开始运行到结束。

此阶段禁止大量生成素材、制作剧情或设计复杂 UI。

### 阶段 B：垂直切片

目标：做出一段接近最终品质的完整体验。

必须完成：

- 一套正式操作手感。
- 一个完整关卡或三分钟内容。
- 正式 HUD。
- 一套正式美术和音效。
- 基础性能检测。
- 大厅、全屏、静音、积分接入。

### 阶段 C：内容完整

目标：完成全部关卡、敌人、技能、道具或难度。

必须完成：

- 全部内容可以正常解锁与结束。
- 数值曲线已初步平衡。
- 不存在阻塞流程的空弹窗或无奖励选择。
- 所有资源可以正确预加载。

### 阶段 D：优化与验收

目标：达到可长期游玩的稳定版本。

必须完成：

- 高负载性能测试。
- 内存和资源清理检查。
- 桌面、全屏和移动端检查。
- 规则边界测试。
- 难度和掉落率复核。
- `lint` 与生产构建通过。
- 在 4399 端口完成实际浏览器试玩。

## 5. 操作与手感规范

### 5.1 输入响应

- 输入到画面开始响应应低于 50ms。
- 点击、命中、放置等操作应在 100ms 内出现可感知反馈。
- 鼠标、触摸、键盘使用同一套世界坐标换算，禁止全屏后命中位置偏移。
- 连续移动不得因靠近建筑、障碍或屏幕边缘而忽快忽慢。
- 移动速度必须按 `deltaTime` 计算，禁止绑定固定帧率。

### 5.2 操作对象必须可预测

- 拖拽前显示半透明预览。
- 放置前显示有效、无效位置和预计花费。
- 射击前显示方向、准星或发射口朝向。
- 自动寻路必须保持朝向与移动方向一致。
- 点击新目标后，单位应改变路线，不得瞬移。

### 5.3 触屏适配

- 关键按钮点击区域不得小于 42×42 CSS 像素。
- 依赖右键的功能必须提供触屏替代模式。
- 依赖悬停的信息必须能够通过点击查看。
- 专家棋盘等大尺寸内容允许滚动，但不能缩小到无法操作。

## 6. 规则与状态机规范

### 6.1 游戏状态必须显式定义

至少区分：

```text
idle / intro / playing / paused / level-clear / won / lost
```

禁止仅靠多个布尔值组合推测状态，否则容易出现胜利弹窗与游戏循环同时运行等问题。

### 6.2 规则逻辑与显示逻辑分离

棋牌、扫雷、匹配、经济模拟等游戏的规则必须写成可独立测试的纯逻辑模块。

规则模块不得依赖：

- DOM。
- Canvas。
- React State。
- 音效。
- 动画帧。

界面只负责提交输入并显示规则结果。

### 6.3 随机性必须可控制

- 地图和资源在开局时生成，探测行为不能临时改变结果。
- 初始局面不得直接生成必消组合、必死位置或不可完成任务。
- 重要调试场景应该支持固定随机种子。
- 随机奖励必须受保底、权重和已有内容约束。

### 6.4 暂停必须冻结整个游戏

暂停时必须冻结：

- 游戏时钟。
- 敌人和单位移动。
- 技能 CD。
- 生成器。
- 临时效果持续时间。
- AI 行为。

暂停不能只遮挡画面。

## 7. 数值与难度规范

### 7.1 先定义时间预算

每局必须先定义目标时长，再反推资源量和速度。

例如十分钟经营局需要共同校准：

```text
总资源量 ÷ 平均生产速度 ≈ 目标开采时长
```

不能分别调整油田容量、管道速度、马车容量和价格后，才发现两分钟结束整局。

### 7.2 难度由多个维度组成

难度至少从以下维度组合：

- 敌人或障碍数量。
- 生命与伤害。
- 移动和弹道速度。
- 预警时间。
- 安全空间。
- 恢复资源。
- 成长速度。
- 任务压力。
- 操作复杂度。

禁止只通过无限增加生命值制造难度。

### 7.3 任务与成长节奏

- 普通阶段任务建议约 3 分钟完成一个。
- 玩家必须在任务完成前感知进度，而不是突然完成。
- 强奖励需要与完成成本匹配。
- 升级选择不能在关键 Boss 阶段弹出空内容或阻塞流程。
- 每个技能等级必须带来可感知变化；满级应产生形态或机制质变。

### 7.4 强力机制必须有成本

以下效果必须配置冷却、消耗、触发窗口、次数或 Boss 上限：

- 全屏清除。
- 百分比伤害。
- 无限控制。
- 大范围聚怪。
- 连续连招。
- 无敌与大量回血。
- 大量召唤物。

### 7.5 失败必须公平

- 玩家应能看见威胁来源。
- 高伤害攻击必须有预警。
- 初局必须提供安全学习期。
- 失败后应显示原因、成绩和改进方向。
- 不得因 UI 遮挡、输入丢失或规则未说明导致失败。

## 8. 关卡、Boss 与剧情规范

### 8.1 关卡必须改变玩法条件

新关卡不能只更换背景颜色，至少改变两项：

- 地形和碰撞物。
- 敌人池。
- 资源结构。
- 移动路线。
- 环境机制。
- Boss 攻击模式。
- 掉落和经济压力。

进入后期后，前期低价值敌人应退出或降低比例；后期敌人更难，但经验和奖励也必须提高。

### 8.2 Boss 规范

Boss 必须具备：

- 明显大于普通敌人的体型。
- 始终可见的名称与生命条。
- 至少两个攻击阶段或攻击方式。
- 地图和剧情身份对应的美术信物。
- 关键攻击的独立预警和音效。
- 战斗中较干净的画面环境。

Boss 出现时应降低普通单位刷新，避免关键攻击被杂兵和特效淹没。

### 8.3 剧情表达

- 剧情必须服务于关卡目标或角色动机。
- 前期使用线索和异常细节，后期再解释真相。
- Boss 战前建立冲突，战中揭示信息，战后推进下一目标。
- 对话必须可以快速跳过或使用调试入口直接预览。

## 9. AI 规范

### 9.1 AI 必须遵守同一套规则

- AI 不得读取玩家不可见信息，除非玩法明确允许。
- AI 落子、射击、移动和资源消耗必须通过正式规则接口。
- AI 不得生成非法动作后直接修改棋盘补救。

### 9.2 AI 至少具备基础策略

不同类型游戏应具备相应判断：

- 棋牌：合法性、提子、气、危险点、局面价值。
- 经营：投资回报、库存、价格和路线选择。
- 战斗：距离、威胁、冷却和目标优先级。
- 竞价：地块价值、资金安全线和对手报价。

### 9.3 AI 需要表现思考过程

- 适当增加 300 至 800ms 的可见思考延迟。
- 长计算应该放入 Worker 或拆帧执行。
- AI 行动后需要明确显示发生了什么。

## 10. UI 与信息层级规范

### 10.1 HUD 优先级

第一优先级：

- 生命或失败压力。
- 当前目标。
- 关键资源。
- Boss 生命。

第二优先级：

- 技能 CD。
- 经验与等级。
- 任务进度。
- 连击与临时增益。

第三优先级：

- 历史最高分。
- 操作提示。
- 非关键说明。

禁止让已完成任务、长期说明或装饰信息长期占据主要战斗区域。

### 10.2 视觉可读性

- 血条、经验条必须有稳定位置与统一样式。
- 友军与敌军必须使用不同描边、血条颜色或阵营标识。
- 技能颜色与地图背景必须保持足够对比度。
- 雪地等高亮地图禁止大面积纯白导致技能不可见。
- 技能图标、Boss 名称和主动技能按钮在全屏模式下必须同步放大。

### 10.3 弹窗规则

- 弹窗必须有明确关闭方式。
- 弹窗打开时需要冻结相关操作。
- 任何选择弹窗都必须保证至少有一个有效选项。
- 不得出现内容为空但仍阻塞游戏的弹窗。

---

## 11. 美术与素材规范

### 11.1 统一风格

同一游戏必须统一：

- 像素密度。
- 描边粗细。
- 光源方向。
- 色盘。
- 角色比例。
- 动画帧率。
- 阴影表现。

禁止同时混用高清平滑插画、低分辨率像素素材和简单 CSS 几何图形作为同等级技能主体。

### 11.2 素材优先级

1. 项目已有且风格匹配的素材。
2. 授权明确的免费素材库。
3. 自行绘制或程序化生成。
4. AI 生成并进行像素化处理。

所有外部素材必须登记作者、来源和许可证。参考商业游戏时，应还原玩法逻辑，但使用原创或已授权的名称与美术。

### 11.3 AI 素材处理流程

```text
确定角色设定与色盘
→ 使用纯色背景生成
→ 检查轮廓与关键道具
→ 本地抠图
→ 裁切透明边距
→ 最近邻缩放
→ 限制颜色数量
→ 放入真实场景验图
```

生成提示必须包含地图、身份、武器、轮廓、关键剧情信物、色盘、像素规格和禁止内容。

### 11.4 地图物件

- 装饰与碰撞物必须符合地图主题。
- 固定地图物件不能因离开视野反复消失和重生。
- 碰撞体积应接近视觉轮廓。
- 障碍物必须提供玩法价值，例如阻挡怪物、躲避弹道或改变路线。

## 12. 动画、特效与声音规范

### 12.1 特效必须表达规则

特效首先用于说明：

- 攻击范围。
- 属性类型。
- 命中时间。
- 友军或敌军归属。
- 连招关系。
- 危险等级。

禁止只增加不表达任何规则的泛白光、透明圆圈和全屏粒子。

### 12.2 特效预算

- 普通命中使用低成本特效。
- 精英、Boss 和大招使用高成本特效。
- 同屏特效超过预算时优先保留危险预警、玩家技能和 Boss 技能。
- 批量死亡时合并粒子、音效和伤害数字。

### 12.3 声音规范

每款游戏至少具备：

- 开始音效。
- 基础操作音效。
- 命中或成功反馈。
- 失败反馈。
- 胜利反馈。

需要节奏感的游戏应增加 BGM。BGM 不得掩盖危险预警、节奏判定和关键操作音效。

音乐游戏必须以音频时钟为准，画面只负责展示，不得用动画帧反推音乐时间。

## 13. 工程架构规范

### 13.1 游戏目录

```text
features/games/<game-name>/
├── Game.tsx
├── Game.module.css
├── Engine.ts
├── types.ts
├── data.ts
├── assets.ts
├── audio.ts
└── rules.ts
```

按实际需要选择文件，但禁止把界面、规则、素材配置、音频和几千行引擎全部放进一个文件。

### 13.2 React 与引擎边界

React 负责：

- 开始和结算界面。
- HUD。
- 设置和暂停弹窗。
- 大厅 SDK。
- 低频状态。

游戏引擎负责：

- 每帧更新。
- 实体位置。
- 碰撞。
- 子弹和粒子。
- AI 高频行为。
- 物理与路径。

禁止每帧更新 React State。HUD 建议每 80 至 150ms 同步一次。

### 13.3 主循环

- 使用 `requestAnimationFrame`。
- 使用 `performance.now()` 计算时间。
- 将单帧 `deltaTime` 限制在合理范围，避免窗口切回后瞬移。
- 复杂物理可以使用固定时间步长并限制单帧补算次数。
- 退出游戏时必须取消 RAF。

### 13.4 资源加载

- 正式开始前预加载关键图片和音频。
- 图片使用统一缓存，禁止每个实体单独创建图片对象。
- 资源失败必须有降级表现，不能阻塞整个游戏。
- 大型资源应按关卡加载并在无用时释放引用。

### 13.5 清理规范

组件卸载时必须清理：

- RAF。
- `setTimeout`。
- `setInterval`。
- 键盘、鼠标、触摸和 resize 监听。
- Worker。
- 音频节点。
- 对 DOM、Canvas、实体和素材的长期引用。

---

## 14. 性能规范

### 14.1 帧预算

目标为普通桌面设备 60 FPS：

```text
单帧总预算：16.67ms
逻辑与碰撞：建议 ≤ 6ms
渲染：建议 ≤ 8ms
浏览器与其他工作：保留 ≥ 2ms
```

高负载场景不能持续低于 45 FPS。移动端可以降级特效，但不能影响规则和输入。

### 14.2 高频场景禁止事项

禁止在每帧中：

- 对所有敌人执行所有子弹的双重遍历。
- 创建大量临时对象和数组。
- 更新 React State。
- 写入 localStorage。
- 创建图片和音频对象。
- 输出日志。
- 对画面外实体执行完整特效和碰撞计算。

### 14.3 大量敌人与范围伤害

必须采用：

- 空间网格或其他邻域查询。
- 对象池。
- 批量伤害与批量击杀结算。
- 伤害数字合并。
- 粒子和音效预算。
- 掉落物合并或吸附批处理。
- 死亡实体及时从活动列表移除。

如果“很多怪物同时受伤”比“很多怪物待机”更卡，应优先检查伤害回调、特效、掉落、任务、经验和声音，而不是只减少怪物数量。

### 14.4 性能压测场景

每款实时游戏至少测试：

- 正常单位数的 2 倍。
- 最大范围攻击命中大量目标。
- 同一帧批量死亡。
- 大量掉落物同时吸附。
- Boss、杂兵、弹道和特效同时存在。
- 全屏切换和窗口尺寸变化。
- 连续运行 15 分钟后的内存情况。

## 15. 类型玩法专项规范

### 15.1 生存 Roguelike

- 职业必须拥有独立技能池和打法。
- 技能满级必须质变，不能只增加百分比。
- 召唤物必须有数量、生命、持续时间和阵营标识。
- 强连招必须有冷却或触发窗口。
- Boss 战降低杂兵刷新。
- 经验球、伤害数字和死亡特效必须批量优化。

### 15.2 经营与物流模拟

- 资源在地图生成时确定。
- 探测只负责发现，不能创造资源。
- 生产、缓存、运输、库存、销售形成闭环。
- 车辆必须显示装载、移动和卸载过程。
- 每种升级必须改变可观察的容量、速度或范围。
- 整局资源量必须按目标时长反推。

### 15.3 音乐游戏

- 使用 Web Audio 时钟和提前调度。
- 音符时间、视觉位置和判定窗口来自同一时间源。
- 不同难度必须重新编排节奏，不只是提高下落速度。
- 音乐波形和视觉旋律必须和实际音乐同步。

### 15.4 棋牌与经典规则游戏

- 规则写成纯函数并做边界测试。
- AI 必须通过正式合法性接口行动。
- 首击安全、劫争、禁入点、计分等规则不能用 UI 特判。
- 必须显示当前回合、结果原因和重新开始入口。

### 15.5 轨道匹配与弹射

- 曲线路径按弧长采样，保证物体匀速。
- 碰撞使用真实半径或线段关系。
- 插入物体时必须正确调整相邻间距。
- 消除后间隙逐渐闭合，并重新检测连锁。
- 初始序列不能自动形成大量消除。

### 15.6 射击与弹幕

- 玩家移动速度必须允许对已预警弹道作出反应。
- 弹幕难度来自组合和空间，不是单纯填满屏幕。
- 激光等高伤害攻击必须先显示预警线。
- Boss 不同阶段必须改变攻击模式。
- 子弹、命中和爆炸使用对象池与数量上限。

## 16. 平台接入规范

每款游戏必须接入：

- 大厅游戏注册。
- 分类与搜索。
- 游戏卡片美术。
- 最近游玩。
- 最高分。
- 玩家排名。
- 全屏。
- 全局静音。
- 操作说明。

游戏不得直接操作其他游戏的存档。成绩通过统一 SDK 提交，当前游客数据保存在本地，未来登录和支付只能通过公共 SDK 扩展。

## 17. 测试规范

### 17.1 规则测试

纯规则模块至少覆盖：

- 正常操作。
- 非法操作。
- 边界位置。
- 连锁情况。
- 胜负结算。
- 重复操作。
- 暂停和恢复。

### 17.2 浏览器试玩

必须实际验证：

- 从大厅可以打开。
- 第一局可以开始。
- 核心操作真实生效。
- 可以胜利或失败。
- 可以重新开始。
- 最高分正常记录。
- 全屏后输入坐标正确。
- 控制台没有错误。

### 17.3 视觉检查

- 关键 UI 没有被裁切。
- 弹窗能够关闭。
- 高亮地图上技能仍清晰。
- 角色和 Boss 比例正确。
- 触屏按钮不遮挡主要内容。
- 19 路棋盘、专家扫雷等大内容仍可操作。

## 18. 新游戏完成定义（Definition of Done）

只有全部满足以下条件，游戏才算完成。

### 玩法

- [ ] 一句核心循环已经真实可玩。
- [ ] 成功、失败、暂停和重开完整。
- [ ] 前 30 秒存在明确正反馈。
- [ ] 至少有一次节奏或策略变化。
- [ ] 不存在阻塞流程的空内容。

### 手感

- [ ] 输入延迟可接受。
- [ ] 全屏和普通窗口坐标一致。
- [ ] 鼠标、键盘和触屏均有可用方案。
- [ ] 关键动作有动画和声音反馈。

### 数值

- [ ] 单局时长符合目标。
- [ ] 普通玩家能够完成早期内容。
- [ ] 强力技能和奖励存在成本。
- [ ] 不存在无限资源、无限回血或无条件清屏。

### 美术与声音

- [ ] 风格、像素密度和色盘统一。
- [ ] 关键角色、敌人和技能不重复滥用素材。
- [ ] 地图背景不会影响玩法信息识别。
- [ ] 素材来源与许可证已登记。
- [ ] 基础操作、成功、失败和胜利均有音效。

### 性能

- [ ] 高负载场景保持可玩帧率。
- [ ] 大量受伤和批量死亡不产生严重卡顿。
- [ ] 粒子、音效、掉落物和伤害数字有预算。
- [ ] 退出游戏后定时器和监听器已经清理。
- [ ] 连续运行不存在明显内存增长。

### 平台

- [ ] 已接入大厅、搜索和分类。
- [ ] 已接入最近游玩和最高分。
- [ ] 已接入全屏和静音。
- [ ] 操作说明准确。
- [ ] `npm run lint` 通过。
- [ ] `npm run build` 通过。
- [ ] 4399 本地页面实际试玩通过。

## 19. 常见反模式

以下情况视为未完成：

- 只有 UI，没有核心因果链。
- 使用大量文字解释本应由动画表达的过程。
- 所有职业、技能或 Boss 只是换颜色。
- 为提高难度只增加血量。
- 为提高爽感加入无成本清屏和无限回血。
- 用随机生成掩盖关卡设计不足。
- 同屏对象多时仍进行全量双重遍历。
- 画面卡顿时只减少内容，不查伤害、特效和掉落链路。
- 弹窗没有关闭按钮。
- 结束、切关或升级时出现空选项并阻塞流程。
- 使用临时素材完成玩法后，从未替换成统一正式素材。
- 只在代码层判断完成，没有实际浏览器试玩。

## 20. 最终决策顺序

开发中发生冲突时，按以下优先级决策：

1. 规则正确。
2. 操作清晰。
3. 核心循环有趣。
4. 性能稳定。
5. 难度公平。
6. 信息可读。
7. 美术统一。
8. 内容数量。

宁可减少一个系统，也不能保留一个没有完成因果链、无法理解或严重影响性能的系统。
